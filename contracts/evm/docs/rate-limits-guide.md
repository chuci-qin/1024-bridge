# Bridge1024 速率限制配置指南

## 函数签名

```solidity
function configureRateLimits(
    uint256 _maxPerWindow,   // 每个时间窗口内允许的最大解锁总额
    uint256 _windowDuration, // 时间窗口的持续时长（秒）
    uint256 _maxSingle,      // 单笔最大解锁金额
    uint256 _maxStake,       // 单笔最大 stake 金额（应匹配对端链的 _maxSingle）
    uint256 _minReserve      // 金库最低储备金（unlock 后余额不得低于此值）
) external onlyAdmin;
```

USDC 精度为 6 位小数：`1 USDC = 1e6 = 1_000_000`。

---

## 参数详解

### `_maxPerWindow` — 窗口最大解锁总额

单个时间窗口内所有 unlock 的累计金额上限。合约使用**滑动窗口**算法（非固定窗口），通过加权上一窗口的剩余时间占比来平滑流量，避免窗口边界处的突发解锁。

- 设为 `0` 表示**不限制**（`_windowDuration` 同时为 0 时速率限制完全关闭）

### `_windowDuration` — 时间窗口时长（秒）

常用值：

| 值 | 含义 |
|----|------|
| `3600` | 1 小时 |
| `7200` | 2 小时 |
| `86400` | 24 小时 |

推荐 **3600（1 小时）**：既能有效限流，又不会因窗口过短导致正常用户频繁被限。

### `_maxSingle` — 单笔最大解锁金额

限制单次 unlock 的最大金额，防止一笔交易吃满整个窗口额度。

- 建议设为 `_maxPerWindow` 的 **30%–50%**
- 设为 `0` 表示不限制

### `_maxStake` — 单笔最大 stake 金额

限制单次 stake 的最大金额，防止用户 stake 后在对端因 `maxSingleUnlock` 限制而无法 unlock。

- 应配置为**对端链 `_maxSingle`** 的值，保证 stake 金额一定能在对端解锁
- 设为 `0` 表示不限制

### `_minReserve` — 金库最低储备金

每次 unlock 后，合约 USDC 余额不得低于此值。这是最后一道安全防线，确保金库不被完全掏空。

- 建议设为金库总额的 **20%–30%**
- 设为 `0` 表示不要求最低储备

## 配置方案

以下方案假设金库初始持有 **100,000 USDC**，根据运营阶段选择。

### 方案 A：保守型（推荐初期上线）

```solidity
bridge.configureRateLimits(
    10_000e6,   // 每小时最多解锁 10,000 USDC
    3600,       // 窗口 = 1 小时
    5_000e6,    // 单笔最大 5,000 USDC
    5_000e6,    // 单笔最大 stake 5,000 USDC（匹配对端 maxSingle）
    20_000e6    // 金库至少保留 20,000 USDC
);
```

| 指标 | 值 |
|------|-----|
| 每小时最大流出 | 10,000 USDC（金库的 10%） |
| 单笔上限 | 5,000 USDC |
| 金库保底 | 20,000 USDC（金库的 20%） |
| 攻击者理论最大损失 | 80,000 USDC（需要 8 小时持续攻击才能耗尽至保底线） |

**适用场景**：刚上线、用户量不大、以安全优先。绝大多数用户单笔 < 5,000 USDC 不受影响。

### 方案 B：适中型（日活跃 TVL 较高）

```solidity
bridge.configureRateLimits(
    50_000e6,   // 每小时最多解锁 50,000 USDC
    3600,       // 窗口 = 1 小时
    20_000e6,   // 单笔最大 20,000 USDC
    20_000e6,   // 单笔最大 stake 20,000 USDC（匹配对端 maxSingle）
    10_000e6    // 金库至少保留 10,000 USDC
);
```

| 指标 | 值 |
|------|-----|
| 每小时最大流出 | 50,000 USDC（金库的 50%） |
| 单笔上限 | 20,000 USDC |
| 金库保底 | 10,000 USDC |
| 攻击者理论最大损失 | 90,000 USDC（不到 2 小时可耗尽至保底线） |

**适用场景**：桥已稳定运行一段时间，日交易量较大，需要更高的吞吐量。需配合更快速的监控告警。

### 方案 C：宽松型（大资金桥）

```solidity
bridge.configureRateLimits(
    200_000e6,  // 每小时最多解锁 200,000 USDC
    3600,       // 窗口 = 1 小时
    100_000e6,  // 单笔最大 100,000 USDC
    100_000e6,  // 单笔最大 stake 100,000 USDC（匹配对端 maxSingle）
    50_000e6    // 金库至少保留 50,000 USDC
);
```

**适用场景**：金库 TVL > 1M USDC，大额跨链需求频繁。必须有 7×24 监控 + 自动告警 + guardian 随时待命。

### 方案 D：测试网 / 开发环境

```solidity
bridge.configureRateLimits(
    type(uint256).max,  // 不限总额
    3600,               // 窗口 1 小时
    type(uint256).max,  // 不限单笔
    0,                  // 不限 stake 金额
    0                   // 不要求最低储备
);
```

**适用场景**：本地测试、测试网部署。**切勿用于主网。**

---

## 选择思路

核心原则：**限额 = 在发现攻击并执行 `emergencyFreeze()` 之前，你能承受的最大损失。**

| 参数 | 定值依据 |
|------|---------|
| `windowDuration` | 通常 **1 小时（3600）** 即可 |
| `maxPerWindow` | 问自己：1 小时内被偷走多少能承受？一般设为金库总额的 **10%–30%** |
| `maxSingle` | 设为 `maxPerWindow` 的 **30%–50%**，防止单笔吃满窗口 |
| `maxStake` | 设为**对端链 `maxSingle`** 的值，保证 stake 后对端能 unlock |
| `minReserve` | 设为金库总额的 **20%–30%**，为应急响应争取时间 |

### 安全与体验的权衡

```
更安全 ←──────────────────────────→ 更好的用户体验
方案 A          方案 B          方案 C
低限额          中限额          高限额
小额用户无感    大多数用户无感    所有用户无感
攻击损失小      需要更快响应      需要 7×24 监控
```

### 建议路线

1. **上线初期** → 方案 A，观察 1–2 周
2. **交易量增长** → 根据实际日均解锁量调整至方案 B
3. **持续稳定** → 视金库规模和监控能力决定是否进一步放宽
4. 每次调整需通过 **timelock 流程**（`scheduleOperation` → 24h → `configureRateLimits`）

---

## 监控建议

无论选择哪个方案，都应配合以下监控：

- **窗口使用率告警**：当 `currentWindowUsage / maxUnlockPerWindow > 80%` 时触发告警
- **大额交易告警**：单笔 unlock 超过 `maxSingle * 50%` 时通知运维
- **金库余额告警**：USDC 余额接近 `minReserve` 时紧急通知 guardian
- **异常频率告警**：短时间内 unlock 频率异常升高时触发
